📋 Table-Driven Routing Protocols
DSDV · WRP · CGSR — These always keep a ready route table, like a GPS that's always updating the map
What is it?

The Big Idea

These protocols keep an up-to-date routing table at every node at all times — even when no data is being sent. Like how a GPS always knows all roads even before you start navigating.

Real Life: Imagine you have a notebook where you constantly write down directions to every person's house in your city — even if you never visit them. That's a table-driven protocol. Always ready, always updated.
Protocol 1

DSDV — Destination Sequenced Distance-Vector

Each node has a routing table with 4 columns: Destination, Next Hop, Distance (hops), Sequence Number. The sequence number is the key magic — it prevents routing loops!

  • Based on the Bellman-Ford algorithm
  • Sequence number always increases — newer = larger number
  • 2 update types: Incremental (small change, 1 packet) and Full Dump (big change, multiple packets)
Real Life: Think of it like WhatsApp "last seen" timestamps. If you get two messages about someone's location, you trust the one with the newer timestamp. DSDV's sequence number works exactly like that — higher number = fresher route. If a node disconnects, neighbours mark its distance as ∞ (infinity) and broadcast that info.

✓ Advantages

Fast route setup. Loop-free. Extends wired protocols easily.

✗ Disadvantages

High overhead when nodes move a lot. Stale info if node waits for destination's update.

Protocol 2

WRP — Wireless Routing Protocol

Similar to DSDV but uses 4 tables instead of 1 for more accuracy:

  • Distance Table — distance + predecessor node
  • Routing Table — shortest path, predecessor, successor, cost
  • Link Cost Table — cost of each link, detects broken links
  • Message Retransmission Table — tracks unconfirmed updates
Real Life: DSDV is like Google Maps showing you just the best route. WRP is like Google Maps PLUS showing you alternative routes, traffic details, road conditions, AND a history of route changes — much more detailed but uses more memory!

✓ Advantages

Faster convergence, fewer updates than DSDV.

✗ Disadvantages

Needs large memory. Not good for large networks with high mobility.

Protocol 3

CGSR — Cluster-Head Gateway Switch Routing

Organises the network into clusters. Each cluster has a leader (Cluster-Head), selected by the LCC (Least Cluster Change) algorithm.

  • Internal Node — regular member, communicates through cluster-head
  • Cluster-Head — leader, schedules routes, forwards to other cluster-heads
  • Gateway Node — belongs to 2+ clusters, acts as a bridge
Real Life: Think of a school. Each class (cluster) has a class representative (cluster-head). If you want to send a message to someone in another class, you tell your class rep → who tells the other class rep → who delivers it. The student who sits between two classes and knows both reps is the Gateway node!

✓ Advantages

Better bandwidth use. Priority scheduling is easy.

✗ Disadvantages

Cluster-head drains battery fast. Frequent cluster-head changes = path breaks.

🔍 On-Demand Routing Protocols
DSR · AODV · LAR · FORP — Only find a route when you actually need one. Like calling a cab only when you need to travel.
What is it?

The Big Idea

Unlike table-driven, on-demand protocols DON'T maintain routes all the time. They only search for a route when a node wants to send data. This saves bandwidth and battery.

Real Life: Instead of memorising directions to every place in the city, you only look up directions when you actually need to go somewhere. Saves effort but takes a little time to find the route when needed.
Protocol 1

DSR — Dynamic Source Routing

The source node discovers the full path to the destination and writes the complete path inside every data packet. 2 phases:

  • Route Discovery: Source floods RREQ (Route Request). Destination replies with RREP (Route Reply) containing the full path.
  • Route Maintenance: If a link breaks, a RERR (Route Error) is sent back to source. Source finds a new route.
Real Life: Imagine sending a letter and writing the full address of every post office it should pass through on the envelope itself — "Go via Bangalore GPO → Chennai Head Post Office → Mumbai Central PO". Each intermediate post office just reads the label and follows it. That's source routing!
Key feature: Each packet carries the complete route. No routing tables at intermediate nodes needed. Uses a Route Cache to remember previously found routes.

✓ Advantages

No periodic hello messages needed. Uses cache efficiently. No routing table updates.

✗ Disadvantages

Broken link doesn't get locally repaired. Small delay at start of new connection.

Protocol 2

AODV — Ad Hoc On-Demand Distance-Vector

Like DSR but instead of putting the whole path in the packet, each node only stores the "next hop" to reach the destination. 3 message types:

  • RREQ — Route Request (sent by source, flooded with TTL)
  • RREP — Route Reply (sent back by destination or intermediate node with cached route)
  • RERR — Route Error (sent when a link fails)
Real Life — AODV vs DSR: In DSR, you carry a full map showing the entire route. In AODV, it's like each road has a signpost saying "next city this way" — you don't need the full map, just follow the signs at each turn (next-hop). AODV uses destination sequence numbers to ensure you always get the freshest, most recent route.

✓ Advantages

Routes on demand only. Uses sequence numbers for fresh routes. Low connection setup delay.

✗ Disadvantages

Intermediate nodes can cause inconsistent routes. Heavy control overhead. Beacon-based.

Protocol 3

LAR — Location-Aided Routing

Uses GPS to limit where route requests are flooded. Instead of flooding the ENTIRE network, it restricts flooding to a specific geographic region.

  • Expected Zone: Area where destination is likely to be (based on past location + mobility)
  • Request Zone: Area where RREQ is forwarded (includes Expected Zone + buffer)
  • LAR 1: Source explicitly puts the Request Zone coordinates in the RREQ
  • LAR 2: Source includes distance to destination; each forwarder checks if it's getting closer
Real Life: Imagine you lost your phone somewhere in Koramangala, Bangalore. Instead of asking every person in all of India if they found it, you ask only people in Koramangala (Request Zone). And you know your phone was last seen near a café there (Expected Zone). Much more efficient than asking everyone!

✓ Advantages

Reduces control overhead. Better bandwidth usage.

✗ Disadvantages

Depends heavily on GPS availability.

Protocol 4

FORP — Flow-Oriented Routing Protocol

Smart protocol designed for time-sensitive traffic (like video calls). Uses prediction to avoid path breaks BEFORE they happen!

  • LET (Link Expiry Time): Predicted lifetime of a wireless link, calculated using position, direction, speed
  • RET (Route Expiry Time): Minimum LET among all links in a path — when this is about to expire, route handoff begins
Real Life: Imagine you're driving and Google Maps says "your current route will have heavy traffic in 5 minutes — switching to alternate route now." FORP does exactly this for network paths! It predicts when a link is about to break and proactively switches to a new path before your call drops. This is called flow-handoff.

✓ Advantages

LET/RET reduces path breaks. Works well in highly dynamic topologies.

✗ Disadvantages

Requires time synchronization and GPS. High control overhead.

⚡ Hybrid Routing Protocols
CEDAR · ZRP — Best of both worlds: proactive for nearby nodes, reactive for far nodes
CEDAR

Core Extraction Distributed Ad Hoc Routing

Selects special "core nodes" (dominators) that form the backbone of the network. Every node is either a core node or is within 3 hops of one.

  • Core nodes handle routing and QoS path computation
  • Increase-waves (slow): propagate when link bandwidth increases above threshold
  • Decrease-waves (fast): rapidly notify when bandwidth drops
  • Finds "shortest-widest path" — shortest path with maximum bandwidth
Real Life: Think of India's highway system. Not every road is a highway — only certain key roads (core nodes) handle the heavy traffic. If a highway's capacity increases (increase-wave slowly spreads the good news), or if traffic jams start (decrease-wave rapidly warns everyone to avoid it). CEDAR does this for data packets using special nodes as the "highway network".

✓ Advantages

Efficient QoS support. Increase/decrease waves manage bandwidth info well.

✗ Disadvantages

Moving core nodes hurts performance. Core updates cause significant overhead.

ZRP

Zone Routing Protocol

Divides each node's "world" into two zones based on hop radius (r). Uses proactive inside the zone, reactive outside it.

  • IARP (Intra-Zone Routing Protocol): Proactive routing inside the zone — routes are always ready
  • IERP (Inter-Zone Routing Protocol): Reactive routing outside the zone — routes found on-demand
  • Peripheral nodes: nodes exactly at the zone boundary (distance = zone radius)
Real Life: Imagine you're in Bangalore. You already know all the roads in your neighbourhood (your IARP zone). But if you need to travel to Hyderabad, you search Google Maps only when you need to go (IERP — reactive). ZRP combines both! Small radius = saves storage but more reactive searches. Large radius = stores more but fewer searches needed.

✓ Advantages

Combines best of proactive and reactive. Reduces control overhead.

✗ Disadvantages

Without query control, can still generate high overhead. Zone radius choice is critical.

🏛️ Hierarchical Routing Protocols ⭐ IMPORTANT
HSR · FSR — Organise nodes in levels or scopes to reduce table size and scale better
HSR

Hierarchical State Routing

Organises nodes into clusters at multiple levels — like a company organisational chart. First level clusters are based on physical proximity (1 wireless hop). Higher levels cluster the leaders of lower levels.

  • Level 0 (Physical): Actual nodes in wireless range
  • Level 1: Cluster-heads of Level 0 clusters
  • Level 2+: Leaders of Level 1 leaders (and so on)
  • Storage needed: O(n×m) vs O(n^m) for flat routing — MUCH less!
Real Life: Think of Indian Army hierarchy: Soldiers (Level 0) → Platoon Commander (Level 1) → Company Commander (Level 2) → Colonel (Level 3). A message from a soldier to another soldier in a different battalion goes up and down the chain. Nobody needs to know every single soldier directly — only their own level's contacts.

✓ Advantages

Reduces routing table size dramatically. Great for military applications with natural hierarchy.

✗ Disadvantages

Overhead in multi-level packet exchange. Leader election is expensive.

FSR

Fisheye State Routing

Inspired by a fish's eye — very sharp focus on close objects, blurry for distant ones. Close nodes get frequent, accurate updates. Far nodes get infrequent, approximate updates.

  • Defines "scopes" based on number of hops: Scope-1 (1 hop), Scope-2 (2 hops), Scope-3 (>2 hops)
  • Updates exchanged frequently with 1-hop neighbours, less frequently for 2-hop, rarely for beyond
  • No flooding — only exchanges with direct neighbours
Real Life: Think about how you know your own street very well (Scope-1). You know your neighbourhood somewhat (Scope-2). But you only have rough knowledge about a distant city (Scope-3). FSR applies this same "sharp focus near, blurry far" principle to network routing — saving bandwidth by not updating distant nodes constantly.

✓ Advantages

Reduces bandwidth usage. Scalable for large, highly mobile networks.

✗ Disadvantages

Performance depends on hop count chosen for each scope level. Needs careful tuning.

🔋 Power-Aware Routing Protocols ⭐ IMPORTANT
5 metrics to choose routes that save battery and extend network life
Overview

Why power awareness matters

In ad hoc networks, nodes run on batteries. A node that dies takes all its routes with it. So routing must consider energy, not just speed. 5 key metrics are used:

MetricGoalSimple Example
1. Min Energy per PacketUse least energy to get from A to BTake the shortest road trip to save fuel
2. Max Network ConnectivityProtect the "cut-set" — nodes whose failure splits the networkProtect the one bridge connecting two parts of a city
3. Min Variance in PowerAll nodes drain equally — no one dies firstShare the carrying load equally among team members
4. Min Cost per PacketBattery-based cost: low battery = high cost = avoidedAvoid sending heavy packages through someone with an injured back
5. Min Max Node CostPrevent any ONE node from becoming too expensive (overloaded)Don't overload one delivery person — spread the deliveries
🌐 Transport Layer for Ad Hoc Networks ⭐ IMPORTANT
Why TCP doesn't work well in wireless networks, and what problems designers face
Issues (9 problems)

Why designing transport for ad hoc is hard

  • 1. Induced Traffic: Wireless broadcast causes a node to receive traffic from many neighbouring paths simultaneously.
  • 2. Throughput Unfairness: Some flows get more bandwidth than others due to MAC and network layer issues.
  • 3. Congestion control must be separate from reliability — congestion is local, reliability is end-to-end.
  • 4. Power & bandwidth constraints — nodes have limited battery.
  • 5. Misinterpretation of congestion: Packet loss in wireless might be due to link errors, not congestion! TCP wrongly slows down.
  • 6. Decoupled layers: Transport must interact with lower layers in wireless (unlike wired where layers are independent).
  • 7. Dynamic topology: Nodes move → paths break → delays in re-establishing.
  • 8. Asymmetric links: Link A→B may be good, but B→A may be weak.
  • 9. Sliding window: TCP's window causes bursty traffic in bandwidth-limited wireless.
Key insight: In wired networks, packet loss = congestion (almost always). In wireless, packet loss can happen due to signal interference, node movement, hidden terminal problem, or battery death — NOT just congestion. TCP doesn't know the difference and wrongly throttles its speed!

Design Goals

A good transport protocol for ad hoc wireless should:

  • Maximize throughput per connection
  • Be fair across all competing flows
  • Have minimum connection setup overhead
  • Handle congestion AND flow control
  • Support both reliable (TCP-like) and unreliable (UDP-like) modes
  • Adapt to topology changes quickly
  • Use battery and bandwidth efficiently
  • Interact with lower layers (cross-layer design)
📡 TCP Protocols over Ad Hoc Networks
TCP-F · TCP-ELFN · TCP-BuS · ATCP · Split-TCP · ACTP · ATP
TCP-F

TCP Feedback (TCP-F)

When a path breaks, the intermediate node (Failure Point) sends an RFN (Route Failure Notification) back to the TCP sender. Sender goes into "Snooze State" — stops sending, freezes timers. When route is re-established, an RRN (Route Re-establishment Notification) wakes the sender up.

Real Life: You're sending WhatsApp messages and your internet cuts out. Instead of your phone madly retrying (which wastes battery), it gets notified "network down — please wait." You pause. When internet is back, you resume. TCP-F does exactly this — prevents useless retransmissions during a path break.
TCP-ELFN

TCP with Explicit Link Failure Notification

When a link fails, the detecting node sends an ELFN message (via ICMP Destination Unreachable) to the TCP sender. Sender pauses and sends periodic probe packets to check if a new route is available. When an ACK returns, normal operation resumes.

Real Life: Imagine you're video calling and the call drops. Instead of your phone endlessly trying to reconnect to the same dead connection, it quietly checks every few seconds "is the network back?" without wasting data. That's ELFN — send probes, wait for a reply, then resume.
TCP-BuS

TCP with Buffering and Sequence Info

More intelligent than TCP-F. When a path breaks, the "Pivot Node" (PN) buffers packets and searches for an alternate path. Uses ERDN (disconnection notification) and ERSN (reconnection notification). LQ and REPLY messages help source know what to resend.

Real Life: You're sending files over a network. The connection breaks at an intermediate server. Instead of telling you immediately, that server buffers your in-transit files, quickly finds an alternate route, and only tells you if it can't fix it. When fixed, it sends "resume from packet 9" — so you don't resend packets 1–8 that were already received!
ATCP

Ad Hoc TCP (ATCP)

Sits between TCP and IP layer. Monitors network conditions and switches TCP into the right state:

  • Normal state: Everything fine, transmit normally
  • Loss state: 3 duplicate ACKs received → retransmit without reducing window
  • Congestion state: ECN received → reduce data flow (real congestion!)
  • Disconnected state: DUR received → pause completely, don't waste packets
Real Life: ATCP is like a smart assistant between you and a customer. The assistant watches network conditions and tells TCP exactly what's happening: "slow down — traffic jam ahead (congestion)", "wait — road is closed (disconnected)", "keep going — all clear (normal)". TCP doesn't need to guess!
Split-TCP

Split TCP

Breaks a long TCP connection into short segments (zones) using intermediate Proxy Nodes. Proxy nodes give Local ACKs (LACK) — they don't guarantee end-to-end delivery but speed up local acknowledgements. Splits the job into: congestion control (local) + end-to-end reliability (global).

Real Life: Think of shipping a package from Bangalore to London via Mumbai. Instead of waiting for London to confirm receipt before Bangalore gets an ACK, the Bangalore warehouse gets a local confirmation from Mumbai ("we have the package"). Mumbai handles getting it to London. The whole chain works in parallel — much faster!

✓ Advantages

Better throughput & fairness. Less impact from node mobility.

✗ Disadvantages

Violates TCP's end-to-end semantics. Proxy node failure hurts performance.

ACTP

Application Controlled Transport Protocol

Gives reliability control to the application itself. Sits between TCP (high reliability, lower performance) and UDP (low reliability, high performance). Application can set packet priority, tolerate some loss, and decide what to retransmit.

Real Life: Like a customizable delivery service. For critical documents — use full tracking. For a casual greeting card — no tracking needed. ACTP lets the APP decide how reliable it needs to be, rather than forcing all-or-nothing like TCP.
ATP

Ad Hoc Transport Protocol

Fully designed from scratch for wireless ad hoc networks. Uses rate-based transmission (not window-based like TCP). Collects congestion info from intermediate nodes and reliability info from the receiver.

  • Quick Start: probes network to find ideal initial transmission rate
  • 3 phases: increase rate → decrease rate → maintain rate
  • Decouples congestion control from reliability
Real Life: TCP is like filling a bucket with water — you keep pouring faster until it overflows (congestion), then reduce. ATP is like a smart irrigation system that asks the soil "how much water can you absorb right now?" and adjusts the flow accordingly — much smarter, no overflow!
